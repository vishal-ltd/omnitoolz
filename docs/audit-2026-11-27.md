# Project audit — 2026-11-27

Independent, full-project audit of OmniToolz at `7c81d6c` (62 live browser tools).
Scope: automated gates, dependency/supply-chain state, security headers and CSP,
privacy and marketing claims, registry↔widget consistency, accessibility, and a
file-by-file review of the shared tool infrastructure with live end-to-end runs of
representative tools against a production build. The previous report
(`docs/audit-2026-11-23.md`) was treated as a claim to re-verify, not as evidence.

Everything below was reproduced locally. Fixes applied in this pass are marked
**fixed**; everything else is reported with evidence and a suggested remedy.

## Method

- Gates on the final tree: `npx tsc --noEmit`, `npm run lint`, `npm test`,
  `npm run build`, `npm run test:smoke` (every sitemap route + headers),
  `npm run test:render` (Puppeteer mounts every widget), `npm audit`.
- Live runs in Chromium against `next start` on a production build: PDF merge,
  PDF→JPG, signature verification (signed fixture), PDF viewer + file hand-off,
  organize-pages, image compression, audio trim/export, regex tester (including
  the catastrophic-backtracking path), hash/JWT/JSON/Base64/word-count/
  case-convert/timestamp tools, and response headers on `/`.
- Static review: shared shell/drop-zone/queue/job/results components, the
  registry and its 62 entries, CSP/headers, privacy/security/about copy, PDF
  and image engines, `public/` provenance docs, CI workflow, README and docs.

## Fixes applied

1. **Signature tool showed a raw DER timestamp (medium).** The report printed
   `Claimed signing time: 261025120000Z` — the ASN.1 UTCTime string, unreadable to
   users. `verify-pdf-signature.tsx` now formats UTCTime (with the RFC 5280
   1950/2049 two-digit-year rule) and GeneralizedTime as a real UTC date
   (`2026-10-25 12:00:00 UTC`), keeping the raw value in an `sr-only` note. The
   existing unit test still asserts the raw lib value; the display layer was the
   gap. **fixed**, verified live on the signed fixture.
2. **Every file input was announced as "Choose files to upload" (low, a11y +
   honesty).** `file-dropzone.tsx` now uses "Choose files from your device"; the
   site never uploads anything, so the accessible name should not say it does.
   **fixed**, verified in the live DOM.
3. **Text Case Converter promised a download that does not exist (low).** Its
   how-to step said "Copy the result or download it as a .txt file", but the
   widget has no download control (copy only). Rewritten to "Copy the result —
   it is ready to paste anywhere". **fixed**.
4. **Merge PDF called its drop zone an "upload area" (low).** Contradicted the
   site-wide no-upload claim; renamed to "drop zone". **fixed**.

## Open findings

### 1. Outcome badges misdescribe nine tools (medium)

`ToolShell` derives its single outcome badge from the *intent* that also groups
cards (`src/components/tools/tool-shell.tsx:14-20`, `src/lib/tools/intent.ts:18`).
Intent describes what the tool does conceptually, not whether it writes a file,
so the badge is false on every text-only tool:

- "Writes a new file — original untouched": Text Case Converter, JSON Formatter,
  Base64 Encode/Decode, Timestamp Converter (all copy results into a box; no file
  is written and there is no original).
- "Generates a new file from what you type": UUID Generator, Hash Generator,
  Password Generator, TOTP Generator (they display text you copy).
- "Writes a new file — original untouched": Color Toolkit (an edit intent, but it
  only converts values).

Only QR Generator (Download PNG) and Invoice Generator (PDF) match their badge.
Evidence: the nine pages were loaded and checked — labels above, zero `a[download]`
elements and no Save button on any of them. Remedy: add an explicit field to
`ToolDefinition` (e.g. `output: "file" | "text" | "none"`) and derive the badge
from it, plus a registry test that fails when a tool has `acceptedFormats: []` but
claims to write a file. Not changed here because it needs a product decision on
new badge wording, not just a typo fix.

### 2. Registry metadata is inert, so it has drifted (medium)

`supportsBatch` and `requiresMultipleFiles` are declared in `types.ts:101-102` and
filled for every tool, but read nowhere else in `src/` — no widget, no test. The
widgets hard-code their own `useFileQueue` options. Consequences found by a
consistency probe over all 62 entries and confirmed in the browser:

- `pdf-to-word`: `supportsBatch: true` with `maxFiles: 1` — the widget is
  single-file (registry.ts:1211-1213).
- `json-formatter`: `acceptedFormats: ["JSON"]`, `maxFiles: 1`,
  `maxFileSizeMb: 5` (registry.ts:1770-1772) although the widget is paste-only.
  Because `ToolShell` keys off `acceptedFormats.length > 0`, the live page footer
  says "Process another file" and "your files are still on this page"
  (`tool-shell.tsx:162-167`) — on a tool that never touches a file.

Remedy: either derive each widget's queue from the registry (single source of
truth) or delete the unused fields and add a test asserting the remaining
metadata matches the widget (file count, formats, size).

### 3. pdf.js worker is a manual pin that can desync (medium)

`pdfjs-dist` is declared as `^4.10.38` (package.json), while the worker served
from `public/pdf.worker.min.mjs` is a hand-copied 4.10.38 build consumed by a
hard-coded path (`src/features/pdf/pdfjs.ts:18`). There is no copy script and no
test or build check tying the two together. Any `npm update`/lockfile refresh
inside the caret range would ship a newer API with the old worker and pdf.js
aborts with a worker/API version mismatch — breaking every PDF tool at once, with
no CI signal (the render check only mounts widgets, it does not open a PDF).
Remedy: pin `pdfjs-dist` exactly, add a copy script and a test comparing the
worker's reported version/hash with the installed package.

### 4. Unused runtime dependency (low)

`@jspawn/qpdf-wasm ^0.0.2` is a production dependency (package.json:24) but no
source or script imports it; the deployed engine is the vendored copy in
`public/qpdf/` (provenance README with matching hashes). It still expands the
installed/audited dependency surface. Remedy: remove it (the vendored files and
their README stay).

### 5. Compress PDF can exhaust tab memory on large batches (low)

The tool accepts 10 × 100 MB (compress-pdf.tsx:86), reads every file fully into
memory, keeps every original and compressed result in the results array
(compress-pdf.tsx:104-124), and instantiates a fresh qpdf WASM module per file
(compress-pdf.tsx:60-83) without reusing or freeing it. Worst case is roughly
2 GB of live buffers in one tab. `useFileQueue` already supports `maxTotalSizeMb`;
using it (and one qpdf instance) would bound this.

### 6. Hand-off silently loses a rejected file (low)

`takePendingFile()` clears the slot before the target tool validates the file
(`src/lib/file-handoff.ts`, `src/components/tools/use-handoff.ts`). Handing a PDF
to a tool that only accepts images therefore shows a format error and discards
the hand-off — the UI still promises "The file carries over — no re-picking
needed". Remedy: validate before consuming, or keep the file and offer to open a
compatible tool.

### 7. Missing HSTS / COOP / CORP headers (low)

`next.config.ts:6-14` sets nosniff, `X-Frame-Options: DENY`, referrer-policy,
Permissions-Policy and CSP (confirmed live), but no `Strict-Transport-Security`,
`Cross-Origin-Opener-Policy` or `Cross-Origin-Resource-Policy`. Vercel adds HSTS
on production deployments, but self-hosted `next start` deployments get none.
Adding HSTS (and COOP/CORP where they do not break anything) to the config makes
the posture deployment-independent.

### 8. Security page links to a policy that isn't in the repo (low)

`src/app/security/page.tsx:37` links GitHub's `security/policy` page, but there is
no `SECURITY.md` (and no `.github/SECURITY.md`); until the repo setting is
configured that link 404s. Add the policy file (or point at the advisory form
only).

### 9. `script-src 'unsafe-inline'` (informational, accepted)

The CSP needs it for Next's inline hydration bootstrap (`next.config.ts:3-4`), and
the only `dangerouslySetInnerHTML` inputs are static, module-level strings. Fine
as a deliberate trade-off; a nonce/hash setup would be the only way to drop it.

## Verified good (spot list)

- No `fetch`, `XMLHttpRequest` or `sendBeacon` anywhere in `src/` — the no-upload
  claim is structurally true, and CDN engine loads (Tesseract) are disclosed in
  privacy §4.
- Exactly three localStorage keys (theme, accent, recent tools), matching privacy
  §3; no cookies; no analytics; no service worker.
- Registry integrity: 62 live tools, unique ids/routes/titles/descriptions, all
  related-tool lists resolve, no server-mode or "upload" claims, JSON-LD properly
  escaped, sitemap/robots/canonicals derived from one site config.
- Blob URLs are revoked (results, file list, recorder, camera, HEIC, edit), the
  regex ReDoS guard works, drop-zone validation rejects empty/oversize/wrong-type
  files with useful messages, and `downloadBlob` cleans up after 30 s.
- Merge/split/organize/compress use pinned, hashed, licensed engines with
  provenance READMEs; signature verification is honest about what a self-signed
  certificate proves.
- Accessibility: skip link, focus-visible outline, `prefers-reduced-motion`
  handling, labelled inputs and `role="alert"` errors; 44 px target-size test.
- README/docs numbers (62 tools, 263 tests, 82 pages, 104 kB shared JS) all match
  the current build.
